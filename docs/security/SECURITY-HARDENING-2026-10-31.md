## Batch 1 completion (2026-10-31): W-12 and W-13
- **W-12 — the remaining `npm audit` highs.** Before: 2 high — `postcss` 8.4.31 bundled inside `next` (GHSA-qx2v-qp2m-jg93, GHSA-6g55-p6wh-862q, GHSA-fxqj-rqcc-2cmp, GHSA-r28c-9q8g-f849; all about processing attacker-supplied CSS, which this site never does — our CSS is our own, compiled at build time) and `zod` 3 (GHSA-mrhx-c7xc-m3w5, memory exhaustion on oversized constrained collections; the only schema, `app/api/wholesale/route.ts`, has no collections). After: `zod` ^4.6.7 (the schema's API — object, string min/max/email, optional, enum, safeParse — is unchanged in v4) and an npm `overrides` entry pinning Next's bundled postcss to 8.5.28 (same major). `npm audit`: **0 critical, 0 high**, 14 moderate. The compiled CSS of a fixtures build is byte-identical with and without the pin (md5 of `.next/static/css/*.css` equal), so the site looks exactly the same. Remove the override when Next itself ships a patched postcss (Next 16 is a separate, owner-scheduled phase; Tailwind stays 3.4).
- **W-13 — `/\host` accepted as a relative link (Low).** Before: `lib/markdown.ts` and `lib/settings.ts` `safeHref`, and `lib/image-hosts.ts` `isOptimizableImage`, treated any value starting with `/` but not `//` as a site path, so `/\evil.com` (which browsers open as another site) passed. All three come from Hub-authored content (blog/FAQ/policy markdown, site settings links, image URLs), so customers could not use it. After: markdown and settings use the shared `isSitePath` (the same check as the sign-in `next`); `isOptimizableImage` refuses a backslash or control character inline (it stays alias-free because `next.config.ts` imports it). Ordinary links render exactly as before (`tests/w13-relative-links.test.mjs`, 3 tests, all failing on the old code; existing markdown/locale tests unchanged).
- **Markdown escape inside a link (found by the independent review of W-13; pre-existing):** a backslash escape inside a link (`[t](/products/k18\_ring)`, `[a\*b](https://x.com/a\_b)`) left the internal placeholder character (U+0000) in the href and the page, because held text was restored in one pass. Now the URL is restored before it is checked (so `/k18\_ring` is the link `/k18_ring`, and an escaped backslash is still refused), and restoring repeats until no placeholder remains. The same review found the line-break placeholder (U+0001) could also reach the page when a hard break sat inside link text or a URL: breaks are now turned into `<br />` after everything is restored, and a URL containing a break is not made a link. Tests added (fail on the old code).
