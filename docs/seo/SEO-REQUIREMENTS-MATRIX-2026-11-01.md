## S. Sitemap reliability — DP-15: APPROVED 2026-11-01 (sub-choice (a); invariant NO), IMPLEMENTED on #468 (not merged/deployed), local proof complete

**Observed [V]:** the first `/sitemap.xml` on the freshly deployed candidate `c6d7cd9` returned 200 with 46 URLs (static pages and categories; no products, no collections); later reads were complete. **Preserved as a failed acceptance assertion (QA §22–§23); a later green read does not erase it.**
**Mechanism [V in source + Next.js docs; which read failed UNVERIFIED]:** `app/sitemap.ts` is a metadata route; Next documents it as cached by default unless a request-time API or dynamic config is used. Its Hub reads use `revalidate: 60`, and the local production build lists `/sitemap.xml` as static (`○`), i.e. prerendered at build and revalidated by time. Every essential read is wrapped in `.catch(() => [])`, and `postLanguages` does `hub.post(slug).catch(() => null)`, which cannot tell "no such language" from "the Hub failed". **Not assumed:** that a previous deployment's sitemap survives a deploy; which read failed; how a failed revalidation behaves for a metadata route on Vercel.

### Specification

**1. Read outcomes (distinguish successful empty data from failed reads).** Every essential read yields `ok(value)` or `failed(reason)`. *Failed* = a thrown error, an abort/timeout, or any non-2xx other than a semantic 404 on a single-post lookup. *Successful empty* = a 2xx with an empty list. A single post lookup answering 404 is a **successful absence** ("this post does not exist in this language"), not a failure.
**2. Essential families** — each must be `ok`: collections, categories, product slugs, posts list, and **every post-language lookup** (`hub.post(slug)` per listable post). **Policy on successful empty lists (corrected): a successful empty list is ACCEPTED for every family** — an empty answer is data, not a failure. A stricter rule exists only as an **explicit catalog invariant that you approve** (DP-15 sub-choice (i): "collections, categories and products must each be non-empty"; recommended, because a live jewelry store with no products is far likelier to be a degraded read than a real state — but it is yours to approve; unapproved = not enforced). No fixed count appears anywhere; no threshold is hard-coded.
**3. Optional resource, kept separate:** the product-image catalog read (`allProducts`, existing 10 s box). Its failure or timeout costs image tags only, is logged once (`sitemap-images-unavailable`), is never retried, never counts toward the essential budget or deadline, and never fails the sitemap.
**4. Abortable deadlines and total budget.** *Per attempt:* 6 s, enforced by an `AbortSignal` passed into the underlying `fetch` (the read really stops). *Retries:* at most 2, only for failed essential reads, after 300 ms then 600 ms. *Per read worst case:* 6 + 0.3 + 6 + 0.6 + 6 = **18.9 s**. *Concurrency:* essential reads in parallel; post-language lookups in waves of at most 8. *Cancellation composes:* each attempt's signal is `AbortSignal.any([AbortSignal.timeout(6000), globalSignal])` — whichever fires first cancels that request; the global signal (one `AbortController`, aborted at the whole-sitemap hard deadline or when one family has already failed) cancels everything still running (`AbortSignal.any` is available in Node ≥ 20.3; CI builds on Node 22; the Vercel runtime version is UNVERIFIED and checked by a test). *Whole-sitemap hard deadline:* **45 s**, aborting everything still running (below Next's documented static-generation default of 60 s per page; hitting it = failed sitemap). *Budget is independent of the optional image read.* **Dependency (honest):** a real abort needs the five Hub read functions (`collections`, `categories`, `productSlugs`, `posts`, `post`) to accept an optional timeout/signal — an additive change to `lib/hub-api.ts`, following the existing `allProducts(limit, { timeout })` precedent — which is the file whose ownership is paused (DP-01b). **Two sub-choices inside DP-15:** **(a) recommended:** the additive timeout parameters, implemented after you name the owner of that file edit; **(b) interim, no `hub-api.ts` change:** a deadline by `Promise.race` — bounded wait, but the underlying request is **not** aborted and runs on until the platform ends it (stated limitation).
**5. Strict vs fixture behaviour (corrected: strictness follows the data source, not the environment name).** *Strict mode* applies in **every deployment that reads a real Hub** — `HUB_API_URL` and `HUB_API_KEY` set and the fixtures flag off — which includes production **and the real-data acceptance preview**: there a failed essential read fails the sitemap exactly as in production, so the preview proves the production behaviour. *Fixture mode* (the repository's fixtures flag, honoured only off production since #467/W-04, or no Hub configured: local development, the CI build, fixtures previews) **keeps today's tolerant static-pages output, separately labelled**: it logs `sitemap-fixture-mode` and has its own tests, and a production deployment with a missing Hub configuration is a *failed* sitemap (never silently fixture). The acceptance preview is therefore strict; fixture builds are visibly different, never mistaken for acceptance evidence.
**6. On failure — option A (the only approval-ready option): fail rather than ship a truncated 200.** The sitemap function throws `SitemapUnavailable` (naming the failed families, no request data).
 - **Build failure:** the static generation of `/sitemap.xml` errors, the build fails, the deployment is not created; the previous production deployment keeps serving (standard Vercel behaviour; **to be demonstrated, not assumed**). Cost: a Hub incident can delay a deploy, including a non-SEO fix; the owner may retry the deploy or roll back the commit.
 - **Runtime failure (revalidation):** **the outcome is NOT assumed.** Acceptance test R decides: **R1** the last good output of that deployment keeps being served and the failure is logged → acceptable; **R2** the error response is served to crawlers → **option A is rejected for runtime** and a separate route-handler design must be specified before approval (see 8).

**7. Tests.** *Unit (mocked Hub, no network; `tests/seo-sitemap.test.mjs` extended):* each essential read failing → `SitemapUnavailable` naming it; successful empty products/collections/categories → throws; successful empty posts → succeeds; a post-language lookup failing → throws; a lookup 404 in one language → that URL omitted, sitemap succeeds; images failing/timing out → sitemap without images, one warning; failure then success within the retry budget → succeeds; retries exhausted → throws; per-attempt abort actually aborts (fake timers + signal observed); the 45 s deadline aborts everything; non-production unconfigured → static pages; production unconfigured → throws; source guard: no `.catch(() => [])` on an essential read; a healthy mock produces output byte-identical to today's (root once, `/en/layaway` once, no `/ja/layaway`, no private route). *Build (local production build, a stub Hub server I control):* healthy → complete sitemap; stub failing on `collections` → `next build` fails with `SitemapUnavailable`; stub failing only the image catalog → build succeeds without image tags. *Runtime and recovery (local `next start`, same stub; finite):* R — build healthy; stub switched to failing; at most one wait of 75 s (the fetch revalidate window is 60 s); then at most 3 requests, 10 s apart → record R1/R2; V — stub restored; poll every 10 s for at most 5 minutes → record the elapsed time to a complete sitemap, or declare **unrecovered** at 5 minutes (a failed acceptance).
